# Аудит управления HyperHDR в AmbiSun

Дата аудита: 2026-08-28
Платформа: webOS, тестовый ТВ `192.168.1.3`
Цель: найти повторные или параллельные команды HyperHDR, фоновые циклы и
лишние пути управления, которые могут вызывать тормоза подсветки.

## Итог

Полная изоляция фоновых механизмов AmbiSun не устранила тормоза. В этой
сборке отключены Activity Manager, автоматическое обновление источника,
стартовые и wake-recovery, автоматическая проверка HyperHDR, Plasma и таймер
часов. После перезагрузки и 20,7 секунды наблюдения диагностика показала:

| Показатель | Результат |
| --- | ---: |
| HyperHDR RPC из AmbiSun | 0 |
| задания автоматики | 0 |
| обновления источника | 0 |
| callback Activity Manager | 0 |
| ошибок RPC | 0 |
| процессов AmbiSun service | 1 |

Следовательно, эти фоновые механизмы не являются единственной причиной
тормозов. Наиболее вероятное направление после этого теста — цепочка
`PicCap -> HyperHDR -> USB-контроллер`, либо конкуренция только в момент
переключения/применения эффекта, а не постоянный idle-опрос AmbiSun.

## Карта текущих HyperHDR RPC

Единственный низкоуровневый HTTP-клиент находится в
`service/com.github.serjio193.ambisun.service/lib/hyperhdr.js`:

- `serverinfo` — проверка состояния и чтение списка эффектов;
- `componentstate` для `LEDDEVICE` — включение или выключение подсветки;
- `effect` — установка эффекта, обычно priority `64`;
- `clear` — очистка эффекта priority `64`;
- `adjustment` — изменение яркости.

UI не обращается к порту HyperHDR напрямую. В текущем `index.html` нет
подключения `js/hyperhdr.js`; интерфейс использует Luna-методы из
`js/webos.js`, а они обращаются к AmbiSun service.

Основные вызывающие пути:

1. `automation.js` — автоматическое правило по источнику, времени и
   конфигурации.
2. `service-hyperhdr.js` — предпросмотр эффекта и его очистка.
3. `service.js` — системная проверка HyperHDR через `serverinfo`.
4. `service-sources.js` — ручная диагностика/получение текущего источника.
5. `scheduler.js` — старый отдельный путь `executeWake`, который в рабочем
   коде не вызывается, но напрямую умеет отправлять `componentstate`.

## Найденные риски

### 1. Нет общей очереди на весь транспорт HyperHDR — высокий риск

`hyperhdr.js` отправляет каждый вызов через отдельный `http.request` и не
имеет общей FIFO-очереди, блокировки или coalescing одинаковых команд.

Очередь автоматики находится только в `automation.js`. Очередь предпросмотра
находится отдельно в `service-hyperhdr.js`. Поэтому они сериализуют свои
собственные операции, но не весь транспорт HyperHDR.

Предпросмотр вызывает `automation.pauseForPreview()`, однако это не отменяет
уже выполняющийся HTTP-запрос автоматики. Если запрос автоматики ещё находится
в полёте, предпросмотр может начать свою команду параллельно. При закрытии
предпросмотра дополнительно отправляется `clear`, а затем выполняется
принудительное восстановление автоматики.

Текущее поведение не доказывает постоянный фоновой поток, но это реальный
риск коротких конфликтов при переключении источника, открытии эффектов и
выходе из предпросмотра.

### 2. Публичный `setLedDevice` обходит очередь — высокий риск при внешнем вызове

Метод `setLedDevice` зарегистрирован как отдельный Luna endpoint в
`service-hyperhdr.js:181-189` и напрямую вызывает HyperHDR. Он не проходит
через очередь автоматики, не проверяет текущий профиль и не участвует в
общем подавлении дублей.

В текущем UI вызов этого endpoint не найден, но сам endpoint опубликован в
`services.json`. Любой старый UI, скрипт или сторонний Luna-клиент может
создать команду в обход защиты.

### 3. `forceApply` отключает верхнеуровневое подавление дублей

В `automation.js:142-147` обычные задания с одинаковым профилем пропускаются.
Но `forceApply=true` обходит это условие. Он используется для:

- `evaluateAndApplyNow` — диагностика и восстановление;
- `preview-resume` — восстановление после предпросмотра;
- recovery-путей в обычном режиме.

Это не является циклом само по себе. Но каждый такой вызов может повторно
проверить и применить профиль. В текущей A/B-сборке recovery отключён, поэтому
контрольный idle-замер не содержал таких команд.

### 4. Восстановление предпросмотра создаёт ожидаемую серию команд

При выборе эффекта UI отправляет предпросмотр. Сервис последовательно может
отправить `effect`, `adjustment`, `componentstate=true`. После очистки он
отправляет `clear`, затем запускает принудительное восстановление автоматики.

Сама серия нужна для функции предпросмотра и не должна работать в фоне. Но
при быстром перемещении по списку и одновременном событии источника возможна
серия коротких переходов. Это главный путь, который нужно профилировать
отдельно от idle-режима.

### 5. Старый прямой web-клиент в версии 0.1.0 — мёртвый, но опасный код

В исходной версии 0.1.0 (`commit 0b70e6c`) `index.html` подключал
`js/hyperhdr.js`. Этот файл содержал прямой browser `fetch` на
`127.0.0.1:8090/json-rpc?request` и функции `setLedDevice`, `getStatus` и
`testLedDevice`.

Поиск вызовов в 0.1.0 нашёл только определения функций, но не нашёл их
использование в UI. В текущей версии файл не подключён. Это не доказательство
причины тормозов, но такой клиент нельзя возвращать без общей очереди.

### 6. Старый `scheduler.executeWake` — отдельный неиспользуемый writer

В `scheduler.js:232-283` остался legacy-путь, который напрямую вызывает
`setLedDevice`. Поиск production-вызовов показал, что сейчас он используется
только тестами; рабочий `service.js` вызывает `scheduler.reconcile`, а не
`executeWake`.

Его следует считать техническим долгом: он способен обойти автоматику, если
его снова подключат в рабочий путь.

## Таймеры и фоновые механизмы

В обычной логике проекта присутствуют следующие источники работы:

- Activity Manager с подпиской на foreground-приложение;
- два Luna-запроса при обновлении источника: EIM и foreground app;
- debounce источника;
- solar Activity Manager для следующего события солнца;
- recovery после старта, сна и ошибки;
- TTL-проверки UI и ручные проверки `serverinfo`;
- таймер предпросмотра эффекта;
- debounce сохранения яркости.

В текущей тестовой сборке фоновые источники и recovery отключены. Сохранились
только пользовательские операции и проверка обновлений приложения. В течение
контрольного замера ни одного HyperHDR RPC не было.

## Activity Manager и жизненный цикл

В обычном режиме `source.js:171-219` создаёт persistent foreground activity с
`subscribe:true`. Callback вызывает `sourceWake`, который запускает чтение
текущего входа и foreground-приложения. Это не прямой HyperHDR RPC, но он
может вызвать автоматическое применение через `onStableSource`.

В `service.js` создаётся один `Service` с одним ID, а automation и HyperHDR
подключаются один раз. На ТВ во время проверки найден один процесс
`com.github.serjio193.ambisun.service`; признаков двух экземпляров AmbiSun не
обнаружено.

## Сравнение с 0.1.0

В 0.1.0 были проще:

- только одна очередь автоматики;
- подавление дублей сравнивало в основном состояние LED;
- recovery после холодного старта использовал `forceApply=true`;
- source-change и recovery могли приходить близко по времени;
- прямой browser-клиент HyperHDR присутствовал в bundle, но не имел найденных
  вызовов.

Текущая версия улучшила подавление по профилю `{state,effect,brightness}` и
добавила сериализацию очереди автоматики. Но общая очередь между automation,
preview и отдельными endpoint так и не появилась. Это главное архитектурное
отличие, которое ещё нужно исправить после завершения измерений.

## Что подтверждено и что пока не доказано

Подтверждено:

- AmbiSun может отправлять `componentstate`, `effect`, `clear` и `adjustment`;
- до диагностического патча разные подсистемы имели разные очереди/пути;
- прямого idle-опроса HyperHDR в изоляционном тесте нет;
- одна копия service запущена от root;
- тормоза сохранились при нулевом числе AmbiSun RPC.

Не доказано:

- что HyperHDR получает повторные команды в обычном режиме именно от AmbiSun;
- что `PicCap` или USB-контроллер являются единственной причиной;
- что оставшийся дефект происходит на старте, при смене источника или только
  при применении эффекта.

## Следующий безопасный шаг

До изменения логики нужно провести запись диагностических событий в обычной
сборке на коротком тесте: сбросить диагностику, выбрать один стабильный
источник, не открывать меню эффектов и снять события через 30-60 секунд.
Затем отдельно повторить тест с переключением источника и отдельно с
предпросмотром эффекта.

Если idle-тест покажет `rpcTotal=0`, а тормоза останутся, AmbiSun в этом
сценарии не является отправителем команд и нужно анализировать HyperHDR/PicCap/
USB. Если команды появятся, их нужно сопоставить с `reason`, `caller` и
источником; общая очередь и suppression уже добавлены в диагностическую
сборку.

## Дополнение: диагностический рефакторинг для теста HDMI4

Разделы выше описывают состояние до диагностического патча. В установленной
тестовой сборке выполнено следующее:

- добавлен `lib/hyperhdr-controller.js` с единой FIFO-очередью;
- automation, preview, ручной LED endpoint и legacy scheduler используют
  controller API;
- повторный `LEDDEVICE` подавляется без HTTP-запроса, включая состояние,
  которое уже находится в очереди;
- preview, очистка preview и список эффектов временно отвечают без HyperHDR
  RPC;
- автоматический `serverinfo` отключён, ручная проверка соединения оставлена;
- добавлены RPC-счётчики, `reason`, `caller`, source events и `instanceId`;
- `forceApply=true` оставлен только для первоначального startup recovery.

На ТВ текущий источник подтверждён как `HDMI_4`. Конфигурация имеет общее
правило `sun`, сейчас день, поэтому recovery корректно выбрал `state=false` и
не отправил команду. За 7,5 секунды после сброса диагностики получено:

- `rpcTotal=0`;
- `serverInfoCount=0`, `componentStateCount=0`, `effectCount=0`;
- `duplicateSkipCount=0`;
- `sourceChanges=1`, `automationEnqueued=1`, `automationEvaluated=1`;
- один запущенный экземпляр сервиса с `instanceId`.

Дальнейшая проверка выполняется только на `HDMI4`; остальные входы не
переключаются.

## Результат дневного теста сна и пробуждения (2026-08-30)

Проведён дневной сценарий сна и пробуждения на тестовом ТВ. После
пробуждения подсветка не включилась, что соответствует действующему дневному
правилу `OFF`.

- лишних команд HyperHDR не обнаружено;
- `ALL` работает корректно;
- теоретический риск в ветке off-recovery на тестовом ТВ не воспроизведён;
- результат этого теста не блокирует выпуск `0.2.8`.

Код по итогам дневного теста не изменялся: проверка зафиксирована как
диагностический результат, а не как подтверждённая неисправность.
