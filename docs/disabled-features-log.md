# Журнал отключённых механизмов AmbiSun

Последнее обновление: 2026-08-29

Документ фиксирует только изменения и тесты, которые уже выполнялись при
поиске причин тормозов на webOS ТВ. HyperHDR, PicCap и системные файлы webOS
не изменялись в рамках этих проверок.

## Сейчас отключено

### Опрос текущего источника каждую секунду

- Файл: `js/bridge.js`
- Было: `getCurrentSource` запускался сразу и затем через
  `setInterval(..., 1000)`.
- Стало: остаётся один запрос при запуске; дальнейшие изменения должны
  приходить через события сервиса. Запрос при возврате приложения из фона
  сохранён.
- Проверка на ТВ: таймер `pollCurrentSource` отсутствует; за 230 секунд было
  только 2 обновления источника.

### Повторный запрос для стартового `ATV`-предпросмотра

- Общий опрос источника не возвращён.
- Если при старте webOS сообщает `ATV`, а на переднем плане находится Home
  (или AmbiSun), это считается последним предпросмотром входа, а не эфиром.
- В этом единственном случае следующий запрос текущего источника выполняется
  через 5 секунд. Если снова получен `ATV`, ставится следующий такой же
  повтор. При реальном HDMI, приложении или Live TV таймер отменяется.
- Пока остаётся только этот предпросмотр, автоматизация и команды HyperHDR не
  запускаются.

### Повторные проверки после запуска

- Файл: `service/.../lib/automation.js`
- Удалены повторные проверки через `5 / 15 / 30 / 60 секунд`.
- Сейчас нет цепочки `STARTUP_RECHECK` и связанных повторных таймеров.

### Проверка состояния HyperHDR каждые 10 секунд

- Файл: `service/.../lib/automation.js`
- Удалён постоянный цикл `STATE_RECONCILE` / `scheduleStateReconcile`.
- В рабочем пути системного статуса `serverinfo` больше не вызывается. Он
  выполняется только по явному запросу интерфейса: тест подключения или список
  эффектов.

### Реакция на `tvpower`

- Файл: `service/.../service.js`
- Подписка и реакция на sleep/wake восстановлены.
- Первое состояние `On` при запуске сервиса не считается пробуждением.
- Реальное пробуждение — только переход `sleep/standby → active`; после него
  выполняется одна отложенная оценка правила.
- Если яркость уже была применена, wake не отправляет повторный `adjustment`.

### Режим полной изоляции производительности (завершён)

Для текущего A/B-теста дополнительно отключены все оставшиеся фоновые
механизмы AmbiSun:

- подписка Activity Manager на активное приложение/источник;
- начальная загрузка кэшей приложений и HDMI в сервисе;
- начальный запрос текущего источника;
- автоматическая проверка системного статуса и HyperHDR при старте;
- автоматическая проверка статуса при возврате приложения из фона;
- автоматическое обновление списка приложений и HDMI при открытии раздела;
- Plasma, включая запуск через пользовательский переключатель;
- восстановление состояния после запуска, пробуждения и ошибок;
- таймер обновления часов.

Этот режим использовался только для A/B-проверки причины тормозов. Он дал
отрицательный результат и больше не является текущим режимом тестовой сборки.

Для нового диагностического теста Activity Manager, source events, recovery и
обычная автоматизация, preview HyperHDR и проверка системного статуса при
старте возвращены. Остаются отключёнными только постоянный опрос источника
раз в секунду и старый цикл `serverinfo` каждые 10 секунд.

## Текущее состояние после восстановления обычной работы

- Проверка системного статуса выполняется после запуска интерфейса и при
  возврате приложения из фона.
- При открытии раздела источников выполняется ручная синхронизация с TTL 20
  секунд; постоянного таймера нет.
- Предпросмотр эффектов снова использует HyperHDR через общую очередь.
- Подписка Activity Manager и tvpower снова активны. После первого стабильного
  источника выполняется одна стартовая оценка; после реального пробуждения —
  только одна отложенная оценка через 10 секунд.
- Системная проверка больше не отправляет тяжёлый `serverinfo` в HyperHDR.
- Recovery после ошибки записи в HyperHDR включён: используются ограниченные
  повторы через `1 / 2 / 4 / 8 / 16 секунд`. Это не является проверкой сигнала
  и не запускается при штатном включении.
- Единая очередь HyperHDR, подавление одинаковых состояний и диагностика RPC
  сохранены.

## Текущий набор подозреваемых

Для следующего теста после текущих изменений остаются:

1. стартовая одноразовая оценка после стабильного источника;
2. одноразовое применение правила через 10 секунд после реального пробуждения;
3. ограниченные повторы только после ошибки записи в HyperHDR;
4. обновление списка источников при открытии раздела;
5. явный запрос списка эффектов;
6. ручной тест подключения HyperHDR.

Системная проверка интерфейса больше не вызывает `serverinfo`. Получение списка
эффектов и ручной тест подключения остаются только пользовательскими действиями.

## Отключалось только на время теста и затем возвращалось

### Фоновая анимация Plasma

- Файл: `js/plasma.js`
- Анимация временно выключалась во время замеров FPS.
- Сам механизм не удалён. При включённой Plasma рендер ограничен 15 FPS.
- При уходе AmbiSun в фон обработчик `document.hidden` останавливает анимацию.
- После завершения замеров Plasma возвращена в меню; текущий дефолт в
  `js/core.js`: `plasma: true`.

### Activity Manager (до режима полной изоляции)

- Файл: `service/.../lib/source.js`
- Подписка Activity Manager временно останавливалась для проверки влияния на
  подсветку, затем была возвращена.

### PicCap

- PicCap временно останавливался как контрольный тест.
- После проверки был возвращён, потому что без него захват изображения не
  работает.

## Что не является постоянным опросом

- Ручные запросы из интерфейса, например открытие проверки HyperHDR.
- Ручной вызов диагностики или системного статуса.
- Обработчики пользовательских действий, если пользователь явно вызывает их.

## Последний замер на ТВ

После перезагрузки сборки в режиме полной изоляции:

- AmbiSun service запущен от `root`.
- HyperHDR и PicCap работают.
- `triggerConfigured = false` для источника.
- `sourceRefreshes = 0`, `sourceActivityCallbacks = 0`.
- `automationEnqueued = 0`, `automationApplied = 0`.
- Единственный `serverinfo` появился из-за ручной проверки `getSystemStatus`.

## Результат полной изоляции

Проверка не дала положительного результата: тормоза сохранились даже после
отключения перечисленных фоновых механизмов. Это исключает их как единственную
причину проблемы, но не исключает влияние самой цепочки захвата
`PicCap → HyperHDR → USB` или другого пути управления HyperHDR.

Следующий этап — глубокий аудит всех HyperHDR RPC, повторных применений,
параллельных клиентов, Activity Manager и жизненного цикла сервиса.

Результат аудита зафиксирован в
`docs/hyperhdr-audit-report.md`: в режиме полной изоляции за 20,7 секунды
получено `rpcTotal=0`, но тормоза сохранились. Найдены архитектурные риски
раздельных очередей предпросмотра и автоматики, а также публичного
`setLedDevice` в обход очереди. Это пока не доказательство причины idle-
тормозов; следующий тест должен разделить idle, смену источника и предпросмотр.

  `OFF` для дневного времени.
